## Not scheduled

- **Do peers prefer holders in their own zone?** Many clusters span zones, and traffic between zones costs more and takes longer: AWS bills about $0.01/GB each way, and a round trip takes about 0.1–0.3 ms within a zone against 0.5–2 ms between zones. Nothing in the swarm knows a node's zone: a lookup answers 8 holders from a random position (D97), and Linux itself has no notion of a zone. A hard split into one swarm per zone sends a zone that lacks a blob to upstream rather than to a peer in the next zone. [Each agent learns its zone from `peer.zone` (live): `"auto"` (default) reads the `topology.kubernetes.io/zone` label of its own `Node` from the apiserver with the kubelet credentials (D16), re-read until the label exists; any other string is the zone; `""` means none. The agent sends its zone in `Hello`; a lookup fills its 8 holders from the asker's zone first, then from the others; `peer.zones = "only"` [`"prefer"`] returns the asker's zone alone, for clusters whose upstream costs less than traffic between zones. The fetcher (D102) tries same-zone holders first. `prewarm.seeds` counts seeds per zone (D51). Peer metrics get a bounded `zone` label, `same` or `other` (D34). To check first: that the Node authorizer lets a kubelet certificate read its own `Node`. Amends D2, D51, D97, D102.]

## In M6

- **Does the gate wait for an image ID that CRI-O's list lacks?** CRI-O rewrites `images.json` before a pull returns (D65), but the agent reads the list again after the change, so a container created right after a pull can name an image ID the agent's copy lacks yet: `image_id` makes it `Unverifiable("image ID is not a config digest")` (D169). [Step 08's wait on a gate miss covers it: the gate waits up to `gate.wait` for the list to name the image ID, as for a verdict still pending. Amends D65, D169.]
- **How does `image_id` refuse an image ID that is no config digest?** With `insecure_allow_unpredictable_image_contents = "true"` in CRI-O's `storage.conf`, a partial pull makes the image ID a TOC digest (D65), yet CRI-O lists the image with the repository digests it was pulled by, so `image_id` maps it to manifests that may be allowed (D169). [The verifier records the config digest of each manifest it verifies, as D65 says, and `image_id` keeps only the manifests whose config digest is the image ID; an image left with none is `Unverifiable("image ID is not a config digest")`. Amends D65, D169.]

- **Which snapshotter holds a containerd 2.3 container whose runtime handler names its own?** containerd 2.3 takes the snapshotter of the pod's runtime handler, `snapshotter` under `[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.<handler>]`, before the images section's (v2.3.7 `internal/cri/server/images/service.go:191`); the `annotation` path Stats only the images section's, so such a container is `Unverifiable("container snapshot cannot be read")` (D170). [The gate reads each handler's `snapshotter` from the config at `Configure` and picks it by `CreateContainerRequest.pod.runtime_handler`. Amends D170.]

## Before M7

- **When does a member release the rest of a prewarm wave?** D51 sends `Prewarm` to the other agents "once the seeds have announced the image's blobs", but a member knows only the image reference, not its blob digests. [The member resolves each `prewarm.images` entry through the registry config (D17) to its platform manifests and their layer digests, and releases the wave once every seed has announced every layer of its platform, or after `prewarm.seed_timeout` (default `300`, live), whichever comes first. Amends D51.]
