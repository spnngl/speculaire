## Not scheduled

- **Do peers prefer holders in their own zone?** Many clusters span zones, and traffic between zones costs more and takes longer: AWS bills about $0.01/GB each way, and a round trip takes about 0.1–0.3 ms within a zone against 0.5–2 ms between zones. Nothing in the swarm knows a node's zone: a lookup answers 8 holders from a random position (D97), and Linux itself has no notion of a zone. A hard split into one swarm per zone sends a zone that lacks a blob to upstream rather than to a peer in the next zone. [Each agent learns its zone from `peer.zone` (live): `"auto"` (default) reads the `topology.kubernetes.io/zone` label of its own `Node` from the apiserver with the kubelet credentials (D16), re-read until the label exists; any other string is the zone; `""` means none. The agent sends its zone in `Hello`; a lookup fills its 8 holders from the asker's zone first, then from the others; `peer.zones = "only"` [`"prefer"`] returns the asker's zone alone, for clusters whose upstream costs less than traffic between zones. The fetcher (D102) tries same-zone holders first. `prewarm.seeds` counts seeds per zone (D51). Peer metrics get a bounded `zone` label, `same` or `other` (D34). To check first: that the Node authorizer lets a kubelet certificate read its own `Node`. Amends D2, D51, D97, D102.]

- **When does a kind suite check mixed versions?** D40's upgrade order rests on a reflector accepting its own protocol version and the previous one; `a_reflector_accepts_the_versions_of_its_range` (`crates/reflect/tests/reflector.rs`) checks it in one process, and no release speaks the reflector protocol yet. [Once the first minor that speaks it is released, the e2e cluster runs that release's agents against the reflectors of the commit under test, on the IPv4 pass, before each minor release. Amends D27, D40.]

- **How is NRI's required-plugin gap closed?** After the agent leaves NRI, by a stop or a kill, the first container created in a pod that already runs passes the required-plugin check. NRI keeps a plugin whose connection closed in its list until the end of the next request of any kind, or until a plugin registers (containerd/nri v0.12.3 `pkg/adaptation/adaptation.go:327`, `:608-632`, `:698`). `CreateContainer` adds every listed plugin to the validation request before calling it (`:341-345`), and a call that fails on the closed connection closes the plugin and answers nothing, not an error (`pkg/adaptation/plugin.go:757-763`). The window is one request, not a time: a new pod's `RunPodSandbox`, or the kubelet removing a container, clears the plugin first. What gets through is a container created in a running pod, such as the kubelet's retry of a container it failed to create, or one whose image finished pulling after the stop. Seen on kind with CRI-O 1.37.2 and containerd 2.4.2 (NRI v0.12.2, v0.12.3), and in a Go reproduction with NRI v0.11.0, v0.12.0, v0.12.2 and v0.12.3: the CRI-O 1.35, 1.36 and containerd 2.3 pins. NRI v0.12.5 fixes it (containerd/nri#338): `CreateContainer` skips closed plugins. No release of either runtime ships it yet; containerd's `release/2.4` has. The gate test `after_a_stop_the_first_container_in_a_running_pod_passes` fails once a runtime ships the fix. A plugin that fails during its own call still counts present under v0.12.5, unless it answers `ConfigureResponse.failure_policy.fail_request` (v0.12.4, containerd/nri#329). The agent's stop order cannot close it: NRI sees the dropped connection only at its next request. A plugin of another name registering clears the closed one; a Go reproduction confirms it. Proposed default: ask CRI-O and containerd to ship NRI v0.12.5 in their supported branches, and answer `fail_request = true` once the NRI proto in `crates/nri` carries it. Until a fixed NRI ships, the agent could register a throwaway plugin after it leaves NRI, and `ExecStopPost` could after a kill.
