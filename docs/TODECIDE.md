## Not scheduled

- **Does spnngl/images check its speculaire image with `speculaire verify`?** D157's `verify` job ran speculaire's own verifier on the image it had just pushed, anonymously and over the public-good TUF root: the project passed its own gate (D28). D194 left that image to spnngl/images and dropped the job, so nothing runs the gate on an attested speculaire image now. [After it signs and attests, spnngl/images's workflow runs `speculaire verify` from that image on the pushed digest, under a policy naming that workflow and requiring its provenance and SBOM, as D157's job did. Amends D28, D194.]

- **What does a seed do when its pull leaves a layer it cannot announce?** A wave's next round waits until the seeds announced every layer of the image, or `prewarm.seed_timeout` (300 s) passed (D185). A pull fetches no blob for a layer the node already holds unpacked, so the agent has nothing to announce for it. containerd reaches that state on a removal while the image's containers still run: its garbage collector deletes the blobs and keeps the snapshots (v2.4.2 `internal/cri/server/images/image_remove.go:44-77`), and the next pull skips them (`core/unpack/unpacker.go:508-520`). A seed in that state holds its wave back the full 5 minutes; the gate suite hit it in CI (#269). Seeds are picked by hash (D181), so the reflector cannot avoid such a node. [After a prewarm pull, the agent fetches through its own mirror (peers first, D102) each layer of the pulled platform manifest it does not hold as a blob, into the content store on containerd and the blob cache on CRI-O, so it announces every layer; `speculaire_prewarm_refetched_total` counts them (D34). To check first: whether CRI-O leaves the same gap when a layer is already in its storage from another image. Amends D185, D188.]

- **Do peers prefer holders in their own zone?** Many clusters span zones, and traffic between zones costs more and takes longer: AWS bills about $0.01/GB each way, and a round trip takes about 0.1–0.3 ms within a zone against 0.5–2 ms between zones. Nothing in the swarm knows a node's zone: a lookup answers 8 holders from a random position (D97), and Linux itself has no notion of a zone. A hard split into one swarm per zone sends a zone that lacks a blob to upstream rather than to a peer in the next zone. [Each agent learns its zone from `peer.zone` (live): `"auto"` (default) reads the `topology.kubernetes.io/zone` label of its own `Node` from the apiserver with the kubelet credentials (D16), re-read until the label exists; any other string is the zone; `""` means none. The agent sends its zone in `Hello`; a lookup fills its 8 holders from the asker's zone first, then from the others; `peer.zones = "only"` [`"prefer"`] returns the asker's zone alone, for clusters whose upstream costs less than traffic between zones. The fetcher (D102) tries same-zone holders first. `prewarm.seeds` counts seeds per zone (D51). Peer metrics get a bounded `zone` label, `same` or `other` (D34). To check first: that the Node authorizer lets a kubelet certificate read its own `Node`. Amends D2, D51, D97, D102.]

- **When does a kind suite check mixed versions?** D40's upgrade order rests on a reflector accepting its own protocol version and the previous one; `a_reflector_accepts_the_versions_of_its_range` (`crates/reflect/tests/reflector.rs`) checks it in one process, and no release speaks the reflector protocol yet. [Once the first minor that speaks it is released, the e2e cluster runs that release's agents against the reflectors of the commit under test, on the IPv4 pass, before each minor release. Amends D27, D40.]

- **Does the agent answer `fail_request = true` once a runtime ships NRI v0.12.4?** NRI v0.12.4 adds `ConfigureResponse.failure_policy` (containerd/nri#329): with `fail_request = true`, a `CreateContainer` call that fails or times out on the plugin rejects the creation instead of letting it through, which today happens even with `required_plugins` (v0.12.3 `pkg/adaptation/plugin.go:757-763`). No release of CRI-O or containerd ships v0.12.4 yet. speculaire subscribes only to `CreateContainer`, so it changes nothing else. Proposed default: yes, once the NRI proto in `crates/nri` carries the field and a pinned runtime ships it; a gate test checks a stalled agent then rejects (amends D9, D41, D180).
