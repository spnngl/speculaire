# Security model

Trust boundaries and accepted risks. Each item names the decision that enforces it. A change that moves a boundary updates this file in the same change.

- **Peers are untrusted for integrity** (*withhold, never forge*):
  - blobs are checked against their digest, and a peer that sends a wrong one is skipped locally for a while; no node can evict another cluster-wide (D7, D52);
  - on the fetch path a peer can only withhold: on containerd the agent sends the runtime no byte of a peer's blob or manifest until the whole has matched its digest, only a blob's head with the size the peer gave, and a blob that fails then goes upstream (D205); on CRI-O it holds back the last chunk, so a wrong blob fails that pull, which kubelet retries without the peers that sent it. A peer that is slow, busy, stalled or gone costs time: the fetcher hedges, moves on, resumes with `Range` from the next, and falls through to upstream when none is left. On containerd what peers send is staged only within `blob_cache.max_size`, claimed at the size the peer gave, so a peer that lies on it fills that bound for one fetch, never the disk; on CRI-O the blob cache counts what it writes against the same bound, evicting to make room. The fetcher dials only the node a lookup named and requires that node's certificate (D16, D52, D67, D73, D102, D205);
  - artifacts are checked against their digest and signature (D8);
- **Peers choose what a tag names (accepted).** With `mirror.resolve_tags` on, the default, a tag resolves to the manifest the first of 2 holders sends (D123). The mirror hashes it itself, so the runtime gets that manifest and only content that matches it, but any node with a node identity can name any manifest of 4 MiB at most for any tag, and a disagreement only logs a warning. A moved tag keeps resolving to the old image while peers hold it. M5's signature check rejects an unsigned image, not an older signed one. `mirror.resolve_tags = false` gives tags back to upstream, live.
  - TUF metadata authenticates itself, so it can travel P2P (D26).
- **Peers are authenticated for identity.** Only holders of a kubelet client certificate from the cluster CA can talk to the peer API or a reflector, and a node can only announce content for itself (D16).
  - **What a node claims:** its name, the `<name>` of `CN=system:node:<name>` under `O=system:nodes`, in a certificate that chains to the cluster CA, carries `clientAuth` and is valid now. Both sides of a link check the same, and a client also checks that the server is the node it dialled (D16, D95).
  - **What it cannot claim:** another node's name, without that node's key or the cluster CA's; any other subject, such as the apiserver's kubelet client certificate (no `O`) or an admin's (`O=system:masters`); a certificate of another cluster. Whoever holds the cluster CA's key, or can make the CSR signer issue for a node name, can be any node.
  - **Where it lives:** the key is read from kubelet's file into memory, and a handshake reads no file. A file whose key does not match its certificate, or whose subject is not a node's, is refused and the pair in use stays (D95).
- **A reflector trusts each node for its own announcements, and bounds them.** It takes a stream's node from the TLS peer's certificate and refuses a `Hello` naming another. It believes what a node says it holds: a lying node can only waste its peers' fetch attempts, since every blob is checked (D7). It holds at most 100k digests for one node, a frame at most 4 MiB, refused from its length before any of it is buffered, a handshake at most 5 s and a silence at most 40 s; a peer address must be an IP literal, so a node cannot send fetchers to a name. Each refusal is counted (D97, D105).
- **An agent trusts the reflector list only from a listed reflector.** It reaches `reflector.url` through a load balancer that is not trusted, so a `Members` answer counts only when the node of the certificate that answered is in the list it returns; any other keeps the previous list. Each member is then dialled at its listed address and must prove that node (D16, D98).
- **A member can make every agent pull (accepted).** An agent takes `Prewarm` and `PrewarmList` only on its streams to members, never from the load balancer (D184). A member, or whoever holds a control-plane node's key, can make every agent pull any image the registry config can reach, one at a time, with the credentials the registry config holds: it costs link and disk, bounded by `prewarm.max_disk_percent` and a list of at most 64 images, and the gate still decides what runs (D188). On containerd, the images its list names stay pinned, out of the kubelet's image garbage collection, until no member lists them; the agent unpins only the pins it marked (D191).
- **After a prewarm pull, the agent on containerd writes to the content store.** It writes only the layers of the platform manifest just pulled that the store holds no blob of, each under its digest, which containerd checks on commit. It fetches each from peers, checked as on the fetch path, else from the endpoints the registry config names but its own mirror, with the node's registry credentials. On CRI-O the relay fetches them into the blob cache, as for a pull (D195).
- **An agent announces only its runtime's `k8s.io` content, or its blob cache.** Content of containerd's other namespaces never reaches a reflector (D99).
- **Lookups tell every node what every other holds (accepted).** Any node can ask any digest and learn up to 8 nodes holding it, with their peer addresses. Which images run where is visible to every node, as to Spegel's DHT (D2, D97).
- **The local mirror is closed to other local processes.** The runtime authenticates with a root-only client certificate, so `hostNetwork` pods cannot read cached layers through it. It listens on loopback only; startup refuses any other `mirror.address` (D14, D56). `configure` writes the keys by temporary file and rename at mode 0600, tightening a looser file, and drops the CA's key once it has signed the two certificates, so no key can issue another client certificate (D55, D82).
- **Pod pull secrets never reach the agent.** On CRI-O the mirror never answers 401, because CRI-O would then send it the pull's credentials, which belong to the upstream registry. It resolves tags with the node's own credentials at upstream, after the peers that hold the tag (D66, D123).
- **On CRI-O the agent is in every pull's path.** CRI-O takes an image whole from the mirror once it serves the manifest, so the agent relays what it fetches from upstream; when the agent is down, CRI-O pulls from upstream (D66). It keeps a blob in its *blob cache*, and so serves it to peers, only once its digest matches; it holds back the last chunk until then, so CRI-O never receives a whole wrong blob (D67).
- **Discovery uses the node's registry credentials on both runtimes.** On containerd too, the agent now reads the logins, CAs and client certificates of containerd's registry config, and sends them to the endpoints that config names for each listed image, and for each manifest the runtime asks the mirror for, never to the node's own mirror (D17, D121, D152). Only the holder of the mirror's root-only client certificate asks the mirror (D14), so only root on the node chooses an image to discover before the runtime lists it. They are held and sent as the relay's are, below.
- **A reflector reads upstream manifests with its node's registry credentials, only to time a wave.** It resolves each `prewarm.images` entry through its node's registry config, never its own mirror, and checks each manifest against its digest. It keeps only the layer digests, to tell when a round announced the image; an upstream that lies can release a round early, or hold it until `prewarm.seed_timeout`, and every agent verifies what it pulls. Only the reflector's config chooses what is prewarmed (D184, D185, D187).
- **Stored artifacts are untrusted; a verified bundle's result is trusted.** The *artifact store* keeps only blobs that match their digest (D7), and a referrer only when its manifest names its target as `subject`; the peer API serves them as they are (D124). A Sigstore bundle counts as the target's signature only once it verifies against the trust root, with a transparency-log entry, and names the target as its in-toto subject or message digest. A `.sig` layer counts the same way only once its simple signing payload names the target in `critical.image.docker-manifest-digest`, checked before any crypto, and it verifies as a v0.1 bundle whose SET is its transparency-log entry (D147). A bundle counts as an attestation only once it verifies so, and its DSSE envelope signs an in-toto statement of the required predicate type; the predicate type of a bundle that fails is read only to pick the reason, which names the policy's predicate type, never the bundle's text (D149). The signature check then keeps who signed it, in memory, for that trust root only, and matches each policy against that signer without verifying again (D145). The store itself stays untrusted: a bundle not yet verified, or verified under another trust root, is verified when a check reads it. Any upstream that serves a listed image can make each node keep, per target, at most 64 referrers of blobs up to `sbom.max_size` each (D121), kept while the image is listed (D131), or for `artifacts.grace` after the mirror is asked for it (D153).
- **Artifacts and their referrers lists come from peers.** Discovery asks the store, then peers, then upstream only when peers give nothing (D126). Checked now: every manifest and blob matches its digest, in flight, and a peer that sends wrong bytes is denied (D52, D102); a bundle counts only when its manifest names the target as `subject`. A peer can list any simple-signing manifest as a target's `.sig`, which names no subject: the signature check rejects one whose payload names another image (D147). A peer can withhold an artifact by leaving it off its list: the verdict engine asks upstream once per listed image before a first `Rejected` (D151), so withholding delays a verdict while upstream is unreachable. Any node with a node identity can make another keep up to the same caps as an upstream can.
- **The relay holds the node's registry credentials, and sends them nowhere else.** They come only from the node's own registry config (D89); a login goes to its own endpoint's `host:port` and not to a redirect's, nor to a mirror's; containerd's `registry.headers` go to every host, mirrors included, as containerd sends them (D78); tokens live in memory per host and scope; every one is a `SecretString` and no header is logged (D37, D88). A client certificate's private key is read at reload and held for the life of the registry config snapshot, as a `SecretString` that `Debug` does not print; the check that parses it makes a copy that is not wiped (D92). A credential, certificate or key file that cannot be used makes its hosts anonymous or without a client certificate, never wider trust (D92). The relay serves only the manifests it fetched for CRI-O and the blobs below them, so the mirror is no open proxy for those credentials (D88). The upstream client alone speaks TLS 1.2, for registries that speak nothing newer; the mirror's own listener stays on 1.3 (D85, D88).
- **Every node verifies for itself.** Verdicts are never shared, and no reflector or peer can relax a node's policy (D26).
- **Who sets the policy depends on the chart's `config.source` (D210).** With `configMap`, the default, whoever can update ConfigMaps in the release's namespace, or upgrade the release, sets the config, the policy and the pinned trust root of every node at once, live: grant that right only to who may relax the gate. With `host`, the agent reads the node's `/etc/speculaire`, read-only, so only who writes the nodes' files does, as under the unit. Either way, whoever can change the chart's DaemonSet or run a privileged pod in its namespace controls the nodes, the gate with them.
- **The trust root comes from a pinned file or from TUF, never from peers.** The pinned file is the node's, or the release's ConfigMap's (D210). A pinned `verify.trusted_root` is read at start, and a corrupt one stops the agent; read again when it changes, a corrupt one keeps the root held (D154). Without one, the agent reaches `verify.tuf_url` itself, anonymously, on the system's trust, and believes only metadata that chains by signature from the TUF root built into the binary; a host that serves that URL can withhold or replay metadata until it expires, never forge it. What `verify.tuf_cache` holds is verified again at each read, as if fetched, and expired metadata leaves the node with no trust root, so verifications end `unverifiable` (D26, D143).
- **Saved verdicts are as trusted as memory.** `/run/speculaire` is root-only, which the agent restores at start (D204), and cleared at reboot; `verify.cache` keeps `cache.bin` there unless the config moves it, to a place that must be as private. A file with an unknown version, a wrong size or a bad checksum is discarded, and entries saved under another policy or trust root only serve as stale verdicts (D31, D165, D176).
- **Secrets never reach a log.** Registry credentials and tokens are `SecretString`s, and HTTP tracing never records headers (D37).
- **The audit log names pods and images.** It is off by default and goes to the root-readable journal (D37).
- **A bad config never loosens the gate.** Unknown keys stop startup, and an invalid reload keeps the previous config, policy file or pinned trust root (D30, D154). A changed policy or root serves the previous verdicts as stale for up to `verify.stale_max` while each image is verified again, so a tightened policy denies after its re-verification, not at once (D21, D154).
- **A policy field the node does not check refuses the policy file.** `keyless.url`, `key.kms`, `static`, a CUE or Rego `policy`, and every other field outside D142's subset stop startup rather than pass images unchecked. A glob matches the repository name, so the tag or digest a pod spec names cannot steer an image off a policy (D142).
- **Private layers are shared, as in Spegel (accepted).** Any node of the cluster can fetch any cached layer without pull secrets. mTLS keeps non-nodes out, but any node can read another node's private layers.
- **The peer API serves any node any blob or manifest it can name (accepted).** It listens on the peer address, to any client with a kubelet certificate of the cluster CA (D16), and answers `GET` and `HEAD` by digest from what the node announces: containerd's `k8s.io` content or the blob cache (D99). A digest is the only key, so a node that learns one, from a reflector's `Lookup` or a manifest, reads that content without the image's pull secret. It serves a tag the runtime lists, as the manifest it holds for that image (D123), and no listing; `peer.max_uploads` bounds what one node can make it send at once (D24, D100).
- **The peer API serves the artifact store to any node (accepted).** To the same clients, it serves each artifact's manifest and blobs by digest, and, in any repository, the referrers of any manifest it holds artifacts about (D124): a node learns which signatures, attestations and SBOMs a node holds for an image, and their annotations, without its pull secret. The referrers index is a hint and not content-addressed: the node that serves it can list any manifest, so a reader fetches each by digest and checks its `subject`, as for any registry's. Those artifacts are as untrusted as the store that holds them; a verdict trusts only what verifies against the trust root.
- **A joining node has no P2P.** Until its kubelet certificate exists, it pulls from upstream; the gate still enforces (D16).
- **The pause image is not gated.** NRI's `PodSandbox` carries no image.
- **On containerd 2.3, the gate trusts the image name annotation only as far as the chain-ID check (accepted gap).** NRI below v0.12.2 names no image, so the gate resolves `io.kubernetes.cri.image-name` in its copy of containerd's image store, and rejects a container whose snapshot does not rest on that image's layers for the node's platform (D170). containerd sets the annotation after the pod's own, so a pod cannot forge it. The check proves the layers, not the config: a retag between pull and create to an image with identical layers but another config, its entrypoint or environment, passes as the image the name names. The snapshot's parent comes from containerd's `/snapshot/prepare` event when it came first, else from a `Stat`, both over containerd's socket (D189). The agent warns at each NRI registration and sets `speculaire_identity_path{path="annotation"}`; containerd 2.4 closes the gap (D15).
- **On CRI-O, the image identity is CRI-O's image ID.** CRI-O sets the annotations that carry it after the pod's own, so a pod cannot forge them. CRI-O passes no pod-spec image name, so every name of the image selects policies, the strictest verdict wins, and an image exemption needs every name (D65, D179). The agent takes the manifests CRI-O's image list gives that ID, and keeps those whose config digest, read from the node, is the image ID (D169, D172).
- **On CRI-O with unpredictable image contents, images are unverifiable.** With `insecure_allow_unpredictable_image_contents = "true"` in `storage.conf`, the image ID is a TOC digest, and a partial pull's layers need not match the signed manifest. No manifest has a TOC digest as config, so the gate makes such an image `Unverifiable("image ID is not a config digest")` (D65, D172).
- **The name the pod asked for chooses its policies, never another name of its image.** One image can have several names on a node under one image ID. On containerd, the image name annotation, the pod spec's string, chooses the policies and the image exemptions once the runtime's image list gives the image that repository; until then, and on CRI-O, every name does: the strictest verdict wins, an unmatched name never lightens a matched one, and an exemption needs every name (D179).
- **Exemptions bypass the gate by namespace or by image name.** A pod in a `gate.exempt.namespaces` namespace starts unchecked before any lookup; `gate.exempt.images` globs match the names that choose the policies, every one of them (D18, D172, D179).
- **Images that no policy matches** are denied by default; `gate.unmatched = "allow"` lets them through unchecked (D23).
- **Admins must allow-list the gate's own dependencies.** With `enforce` + `required_plugins`, a stopped agent blocks every container creation on the node, including control-plane static pods. One container gets through ungated: the first created after the agent leaves NRI, in a pod that already runs, while the runtime ships NRI before v0.12.5 (D180). `gate.exempt` (D18) and the NRI tolerate annotation are the escape hatches. Admins configure them before turning on `enforce` (`docs/operations.md`). `unconfigure` refuses to run while `required_plugins` names speculaire (D32).
- **The tolerate annotation is a pod annotation (accepted).** Anyone who can create a pod can set it, and that pod starts ungated whenever the agent is not registered with NRI (`containerd/nri` `pkg/plugin/annotations.go:40-59`). v1 ships no admission policy to restrict it. The DaemonSet's own pod carries it (D44).
- **The NRI socket is trusted for what it says, and bounded for how it says it.** Its peer is the runtime, root on the node: the plugin believes its runtime name and version, NRI version, timeouts, pods, containers and each CreateContainer's pod and container as sent. It bounds the encoding, not the content: a frame of at most 4 MiB plus 10 bytes and 256 queued per connection (D163), a ttrpc message of at most 4 MiB, refused from its length before any of it is read, at most 256 CreateContainer requests answered at once, each dropped at its deadline, and a request that does not decode is refused on its own stream (D166). A CreateContainer request is read in place: the fields the gate reads must decode, the others are skipped by wire type unchecked (D189). A broken frame or an oversized message ends the session; the runtime then starts containers as NRI's own rules say (D41). The agent dials, as root, the path `nri.socket` names (default `/var/run/nri/nri.sock`), so whoever can bind that path plays the runtime: root, since NRI creates its directory at mode 0700 (v0.12.3 `pkg/adaptation/adaptation.go:641`). A `Configure` that names a runtime other than the one detected on the node closes the connection until the agent restarts (D64, D168).
- **Identity regexes match the whole SAN and issuer.** A `subjectRegExp` of `https://github.com/myorg/` does not pass `https://github.com/myorg-evil/…`, as it would in cosign and policy-controller; a pattern that does not parse alone refuses the policy (D136).
- **`.att` tags do not count.** Attestations are verified only as Sigstore bundles found as OCI referrers; `.att` and unsigned `.sbom` tags are ignored (D12, D43).
- **A BuildKit SBOM is trusted through the index signature.** It has no signature of its own; it counts only when an authority's signer signs the index digest, and the stored index lists its attestation manifest, whose in-toto layers are read unsigned (D12, D49, D150). The record naming the attestation manifest stays untrusted. A blob listed above `sbom.max_size` is never fetched; its listed size, untrusted, only picks the reason, as does its predicate type annotation (D150).
- **Metrics are readable by anyone who can reach the node.** `/metrics` is plain HTTP on every address by default; it holds counts only, no secret and no pod or image label (D34, D42, D45, D50).
- **A gate timeout lets one container through (accepted).** NRI closes a plugin that misses `plugin_request_timeout` and starts that container ungated; D41 keeps the gate's answer under half the timeout and alerts on it.
- **The image users run comes from spnngl/images.** It builds, signs and attests `ghcr.io/spnngl/images/speculaire`. `ghcr.io/spnngl/speculaire` holds unsigned `dev-<commit>` images that anyone who can dispatch `image.yml` on any branch can push. Keep it out of production policies (D194).
- **The agent runs as root** with no capabilities, a read-only system and a syscall filter that denies io_uring (D4, D53).
- **The chart's pod hardens less than the unit (accepted).** Its agent runs as root with no capability in any set, `NoNewPrivs`, a seccomp filter and a read-only root, reads the node's directories through mounts read-only below too, as the chart asks of kernels from 5.12, and writes only to its state, its run directory and the runtime's mirror config; e2e reads these from `/proc` on every node (D211). The filter is the runtime's default profile, broader than `@system-service`, and denies io_uring only where the runtime's own profile does. The pod has no equivalent of `RestrictAddressFamilies`, `RestrictRealtime`, `RestrictSUIDSGID`, `MemoryDenyWriteExecute`, `LockPersonality` or `SystemCallArchitectures`. The others of D53 hold through the container: no capability, the runtime's masked and read-only `/proc` and `/sys`, its own `/dev` and `/tmp`, and no home directory. Under SELinux the pod needs `seLinuxOptions: {type: spc_t}` to reach the runtime's sockets, which lifts SELinux's confinement of it.
- **The gate cannot be switched off.** No setting disables it, and a runtime with NRI disabled stops startup (D64); `audit` mode is the only way to admit everything, and it stays visible in metrics (D54).
